计费链路能不能全 AI 自动化——我的真实答案

发表于2026-11-02|更新于2026-11-02
|浏览量:

做金融后端做久了，会冒出一个念头：这套东西能不能全交给 AI？需求来了，Agent 理解、写代码、跑对账、上线、出问题自己修。人只在边上看着。我认真想过这个问题，结论是：能自动一大部分，但”全”自动化在金融场景里是危险的想法。

先说能自动的部分

需求到代码：计费业务规则高度结构化。”JP 区域期权持仓按日计息，费率取前一交易日收盘价，节假日顺延”——这种描述喂给 Agent，它能把状态机骨架、费率查询、日切逻辑生成得七七八八。前提是领域知识库够厚，这正是我们做的那个计费排查 Agent 沉淀的东西。

异常排查：线上告警来了，Agent 拉日志、对账单、费率快照，定位是哪一环出的问题。这块我们已经落地了，效率提升很明显。人的角色从”翻日志”变成”看 Agent 给的结论，拍板下一步”。

对账生成：新旧系统双跑，对账规则、字段映射、差异报告——Agent 生成模板，人审核。比手写省事太多。

必须人兜底的部分

资金写操作。这是硬红线。Agent 永远不应该有”扣钱”的权限。原因不是技术做不到，是责任归属——一旦真扣错账，必须能指向一个具体的人做了具体决策。机器决策的钱出错，连追责都难。所以我们的计费 Agent 设计成只读：查规则、查快照、查对账，禁止任何资金写操作。这个边界不能松。

新业务首次上线。灰度方案、回滚阈值、哪些存量会受影响——这些判断依赖对业务全局的理解，Agent 给建议可以，拍板得是人。结构化票据那次灰度，Agent 能算出”切 1% 流量影响 X 个账户”，但”先切 1% 还是 5%”是权衡风险和进度的决策，得人定。

口径争议。两个团队对同一个指标的算法不一致，Agent 解决不了——这不是技术问题，是组织问题。Agent 能把两种口径的差异列清楚，但选哪个是业务决策。

为什么”全”自动化是危险想法

金融场景有个特殊性：错误的成本不对称。多算一分钱的收益，和少扣一分钱的费用，后果完全不一样。收益算多了，客户高兴，问题藏着；费用扣错了，客户投诉，监管介入。这种不对称意味着，自动化系统必须偏向”宁可不做，不可做错”。但 AI 的本质是概率性的，它会犯错——在大部分场景犯错可接受，在钱上不可接受。

所以全自动化是个伪命题。真正的目标是把人从重复劳作里抽出来，保留在关键决策点上。Agent 干体力活，人干判断活。理想状态：一个人配一个 Agent，能干原来五个人的活，而不是五个人被 Agent 替代。

我现在做到哪一步

老实说，离理想还远。现在 Agent 主要在排查和知识查询上发力，代码生成还在试，对账生成在用。最大的瓶颈不是 AI 能力，是信任——你敢不敢让 Agent 改一行影响钱的代码。这个信任不是靠模型变强建立的，是靠一次次”它确实没出错”积累的，慢，但没有捷径。

也许哪天我会改主意，觉得某些环节可以放手。但那天不会是因为模型又涨了多少分，而是因为我亲眼见过它在对的边界上做了对的事，很多次。
