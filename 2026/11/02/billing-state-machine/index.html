证券计费计息系统的状态机与资金安全设计

发表于2026-11-02|更新于2026-11-02
|浏览量:

富途证券收费计息系统的核心链路：计息 → 资金冻结 → 扣费 → 解冻。每一步都在动钱，任何一个环节失败都不能留下不一致的账。这篇文章记录这条链路的设计思路。

为什么是状态机

计费订单从创建到终结，每个订单在任意时刻只能处于一个明确状态：

状态机解决了两个问题：

  1. 每一步迁移前置条件明确。扣费只允许从 FROZEN 迁出，没冻结就扣费属于系统 bug，直接告警。
  2. 异常恢复有据可查。FAILED 状态的订单记录失败发生在哪一步，补偿任务按步重放，不重头再来。

月末大批量计费的 WorkerPool 优化

月末计息是集中爆发的批处理，几百万账户要在一夜之内算完。最初的实现是每个 goroutine 各自拿 MySQL 连接写库，高峰期数据库连接池被打满，任务互相争抢。

改法是 WorkerPool 固定并发度：

  • worker 数与 DB 连接数配比固定，避免 goroutine 数量失控拖垮连接池。
  • 任务粒度按账户拆分，单个账户计费失败不影响整批，失败账户进重试队列。
  • 幂等控制：每笔订单带唯一业务号，重试前先查状态，已完成直接跳过。

配合失败补偿与告警体系，批处理任务从”跑完才知道错”变成”错一笔报一笔”。

新旧接口双读对账

风控接口迁移时新旧系统并行。做法是双读：请求同时打到新旧两个接口，以旧接口结果为准写库，新接口结果留档比对。对账任务按日跑批，差异超阈值即告警。对账稳定后再切流，数据一致性有完整证据链。

时态快照模型：期权计费迁移

港股期权从 Python 迁 Go，难点在计费依据是”当时看到的费率”，不是”现在的费率”。时态快照模型把每个计费时点的费率、持仓、规则版本固化成快照：

  • 双跑对账：新旧系统同时消费同一事件流，各自产出账单，逐字段比对。
  • 灰度切流：按客户维度小流量切换，出问题即时回切。
  • 试算与真实扣费严格隔离：试算链路只读，扣费链路独立部署独立权限，防止试算逻辑误触资金。

迁移全程业务无感知。

写在最后

计费系统的所有设计最终指向一件事：每一分钱的变化都有迹可循。状态机保证顺序，幂等保证不重复，对账保证不错账，快照保证可回溯。
