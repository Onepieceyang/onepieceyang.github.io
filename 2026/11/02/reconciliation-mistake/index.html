双跑对账跑了三天，差异就是不为零

发表于2026-11-02|更新于2026-11-02
|浏览量:

期权计费从 Python 迁 Go，上线前的流程是双跑对账：新旧系统吃同一份事件流，各自算账，逐字段比对，差异为零才算过。听起来很简单的一个动作，我们卡了三天。

第一天：差异一大片。

老系统的金额是 Decimal，新系统 Go 侧一开始用了 float64。我下意识觉得”这不至于吧，误差都在小数点后十位开外”。但对账是逐字段比，而且费率计算是连乘——十几个费率因子一路乘下来，第 8 位小数的误差被放大到分级。教训：涉及钱的计算，容器类型没有商量余地，Go 里直接上 decimal 库，入库字符串化，别让 ORM 偷偷转类型。

第二天：差异收敛到个位数，但清不掉。

对不上的是几笔”看起来随机”的订单。查了半天，是时区。老 Python 服务的计息日切分用的是服务器本地时区，某台机器配的 UTC，某台配的 UTC+8，日切边界上的订单归属日期就不一样。这个 bug 其实在老系统里就存在，只是一直没暴露——迁移对账反而把它翻出来了。这种事挺讽刺的：你以为你在验证新系统，其实在给老系统做免费体检。

第三天：差异只剩一笔，一个客户，每天都不对。

最后发现是快照时机问题。计费用的是”当天 0 点的费率快照”，但这个客户的费率恰好在 0 点整被修改过，新系统的快照取到了修改后的值，老系统取到修改前的。边界条件：“0 点的快照”到底含不含 0 点那一刻的变更，两边理解不一致。定了规矩：快照取区间左闭右开，写进文档，两边代码都按这个来。

零差异之后才是切流。回头看这三天，真正花时间的不是写对账逻辑，是判断”这个差异是 bug 还是有合理原因”。每一笔差异都得有人肉眼看、翻两边的日志、找到根因。对账系统最大的成本从来不是机器，是人不肯放过任何一个差异的那股劲儿。

现在切流早就完成，那套对账逻辑还在跑，变成了日常的账务巡检。当初为迁移写的代码，最后留下来干别的活了——这大概是这类项目最划算的部分。
